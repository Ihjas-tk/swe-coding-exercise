A2

New words for this sheet

chunk
One index card: a small piece of text (a paragraph group, one table row, one figure…) that search can return on its own. Always from exactly one page.
token
Roughly a word or part of a word. Chunk sizes are measured in tokens. The code estimates: words × 1.33.
prefix
A label stuck on the front of every chunk saying where it came from: document title › section › page.
keyword search (BM25)
Finds chunks that share words with the question, scoring rare words higher. Fast and exact, but blind to synonyms.
embedding
A list of 768 numbers that represents what a piece of text means. Texts with similar meaning get similar numbers.
dense search
Search by meaning: turn the question into an embedding and find the chunks whose embeddings are closest. Catches synonyms, but weak on exact numbers.
reference numeral
The numbers in patent drawings that point at parts ("160"). The patent text says what each one is ("a control unit 160").
identifier
Anything that must match exactly: part numbers (FVT-ESC-40A), patent numbers, "FIG. 2", values with units (320 A), reference numerals.
VLM
Vision-language model: an AI that can look at an image and describe it. Here, Claude Haiku describes each figure once, during indexing.
FTS5
SQLite's built-in full-text search engine. It does the BM25 keyword search, so no separate search server is needed.
Part B

Step 2, Indexing, slowly

B1

Why not just give Claude all the documents?

For 7 small documents you nearly could. But the brief says the system must work on a 100-page PDF and on a hidden test set, and answers must cite the exact page. Indexing solves three problems:

Size

Hundreds of pages don't fit well in one prompt, cost more, and make the model more likely to miss a detail. Small pieces let us send only the relevant ones.

Citations

If every piece belongs to exactly one page, then "the answer came from this piece" automatically means "the answer is on this page".

Finding needles

Questions here hinge on things like "320 A", "FVT-ESC-40A" or "160". Ordinary search handles those badly unless the index is built to match them exactly.

The README lists a "whole corpus in the prompt" baseline as future work, to check that retrieval actually beats the simple approach on a corpus this small. Expect to be asked about it.

B3

Cutting the notes into chunks

A chunk is what search returns, so its shape decides what search can find. The rule of thumb: one chunk = one thing a question could be about. A table row is one fact; a patent claim is one complete statement; a figure is one picture. So the chunker makes six kinds of card, each cut differently. Each CSV/XLSX row as one line of text, so a row can be found by search too. Counting and totals still go to SQL (sheet 3).

Why the prefixOn its own, "Max discharge current | 320 A" doesn't say which product. The prefix "EV-BMS-100 Battery Management System › 3. Electrical Specifications › p.2" puts the product name and section on the card, so a question that mentions "EV-BMS-100" can find it. In the research notes behind the code, this was the one chunking trick with consistent measured gains.
Why rows, not just whole tablesA row card is small and about exactly one fact, so it scores highly for a question about that fact. Keeping row boundaries was a large win in table-retrieval studies. The whole-table card is kept as well, for questions that span rows.
Also droppedHeadings don't become cards; they become the section part of the prefix. Page headers and footers, plus any short line that repeats on 3 or more pages, are thrown away, so "US 8,485,576 B2 Jul. 16, 2013" on every page doesn't pollute search.
▸ In the code

ae/index/chunker.py: chunk_document walks each page's blocks in reading order and calls _emit_table or _emit_figure, or packs text. row_text builds the "Table: … | col: value" line. _merge_small folds a tiny leftover text chunk (under 60 tokens) into the previous one on the same page and section. running_lines finds repeating headers. structured_chunks reads the spreadsheet rows back from SQLite.

Sizes: TARGET_TOKENS 300, MAX_TOKENS 450, MIN_TOKENS 60, BIG_TABLE_TOKENS 400. There is no overlap between text chunks; the docstring notes that simple size-bounded packing measured as well as "smart" chunking.

Chunk ids read like addresses: EV-BMS-100_design_document.pdf#p2#table_row3 = document # page # kind + counter.

To see chunks drawn on the actual pages: uv run python plots/plot_chunks.py, then open plots/out/chunks/index.html.

B4

The patent part-number dictionary

Patent drawings label parts with bare numbers. A question like "What is labelled 160 in the gripper patent?" can't be answered from the drawing alone: the drawing just shows "160". The meaning is in the text, where every patent says something like "…preferably controlled by a control unit 160."

So this station reads all the patent text and builds a dictionary from the pattern "some words, then a number". Here is what it found for the gripper patent:

… 16 entries for this patent, 47 across the corpus

Not every "word + number" is a part

The pattern also matches "claim 1", "FIG. 2", "10 Hz", "16-bit", "about 96", years and patent numbers. These are filtered out by a stop-list of words that come before them ("claim", "fig", "about"…), a check for a unit right after the number, and a rule that skips 4-digit numbers of 2000 or more. Design documents don't use reference numerals, so there a number must appear at least twice before it's kept. The tests check that the design docs end up with no numerals.

Why trust text over the drawingReading labels off patent drawings is unreliable: the best published results for drawing-label recognition are around 71% (F1). The text is exact. So the text is the source of truth, and OCR from the drawing is only used to confirm which numerals appear in which figure.

Repairing OCR'd labels with the dictionary

Sheet 1 mentioned that Tesseract misreads drawing labels, because the pointer line touches the "1". Here are the real number tokens OCR read off the gripper's FIG. 2, and what the dictionary did with each:

The safety ruleA token is only "repaired" when exactly one dictionary entry could explain it, either by adding one missing leading digit or by swapping a commonly confused digit (1↔7, 6↔8, 0→8). If two entries could explain it, it's left alone rather than guessed.
▸ In the code

ae/index/numerals.py: extract_numerals runs the pattern (DEF_RE) with the filters (STOP_BEFORE, UNIT_AFTER_RE). _clean_name trims "under control of a gate" down to "gate". It handles lists too: "valves 74 and 76" gives two entries.

extract_figure_defs finds sentences like "FIG. 2 is a perspective cross section of…" and stores them as figure titles (20 in the corpus). reconcile_labels is the repair step above. NumeralIndex holds it all; glossary produces "160 = control unit" lines; save/load store it in the numerals and figure_defs tables.

Tests: tests/test_chunker_numerals.py (dev-set numerals, suffixed numerals like 120a, design docs having none, the leading-digit repair).

Why "also defined on this page"OCR never read "160" off this drawing; the README notes the label sits outside the embedded image. The text on the same page does define it, so it's added in a separate, clearly marked field. That way a question about "160" can still reach this figure, and the answering step knows it's weaker evidence than a label seen in the image.

The AI description (station 4)

Each figure image goes to Claude Haiku once, with the caption and the dictionary. It's asked for JSON: figure type, a one-line summary, labelled parts, counts with every counted item listed first, connections, visible text, and what it's unsure of. It's told to report only what's visible.

The answer is cached on the image's fingerprint, so re-runs cost nothing. For questions like "how many M12 ports?", the image itself is also sent to Claude at answer time (sheet 4), because text descriptions alone measured about 24% worse on visual questions.

ae/index/vlm.py → describe_figure (prompt in SYSTEM, one retry, cache in data/cache/vlm.sqlite) and description_text, which flattens the JSON into the line that gets indexed. The model is set by AE_VLM_MODEL (default claude-haiku-4-5-20251001). The full JSON is also kept in the figure_descriptions table.

B7

Two ways to search, and why we need both

search 1

By words (keyword / BM25)

Find cards containing the question's words, with rare words counting more. It's exact, so it's great for "320 A", "FVT-ESC-40A" and "160". But it doesn't know that "IP rating" and "ingress protection" mean the same thing.

Built into SQLite (FTS5). Actually three indexes: normal words (with "currents" matching "current"), exact identifiers, and partial identifiers for typos like "ESC-40".

search 2

By meaning (embeddings)

Each card was turned into 768 numbers by a local model. The question is turned into 768 numbers too, and the closest cards win. It catches paraphrases ("how hot" ≈ "operating temperature"), but it's poor at telling 320 from 330.

Model: IBM granite-embedding-english-r2, running on your machine. Closeness is cosine similarity: 1.0 means the same meaning.

The takeawayEach search has blind spots the other covers. So step 3 (retrieval, next sheet) always runs both and merges the two ranked lists. That merge is where the system gets its accuracy.
▸ In the code

ae/index/store.py → IndexStore. keyword_search runs up to three FTS5 queries (chunks_fts prose, chunks_ids exact, chunks_tri trigram), scales each so its best hit scores 1.0, weights them 1.0 / 0.6 / 0.2, and adds them up. Scaling matters: without it, every card that merely mentioned "EV-BMS-100" outranked the row that answers the question. Question words are joined with OR and quoted, because a bare FTS5 query means AND and a hyphen would be read as NOT.

dense_search loads all vectors into one numpy matrix and compares the question against every card (brute force). That's fine up to about 100,000 chunks.

ae/index/embed.py → embed_texts runs sentence-transformers on CPU with a cache in data/cache/embeddings.sqlite keyed by text fingerprint. embed_chunks embeds prefix + text. SPECS records that bge models need a "Represent this sentence…" prefix on queries and granite needs none.

B10

Choices left out, and known limits

No AI-written chunk summaries

Some systems ask an LLM to write context for every chunk. The research notes found the gains didn't replicate reliably, so the cheap, predictable prefix is used instead.

No overlap between chunks

Text chunks don't share sentences. Combined with "never cross a page", every chunk maps to exactly one page for citing.

The dictionary is pattern-based

"left and right wings 14, 16" gives both numbers the whole phrase as a name. A numeral reused for different parts in different figures isn't told apart.

Embedding is slow

granite takes about 50 ms per chunk on CPU, roughly 15 minutes for a 100-page document. Switch to bge-small for 10× faster ingest at a small accuracy cost.

Keyword search alone gets fooled

For our own example question, keyword search ranks a test-log row first (it contains "EV-BMS-100" as an identifier) and the answer row second. That's why the two searches are merged (B7).

Some ids aren't caught

"IP67" has no hyphen and no unit, so it isn't recorded as an identifier. Prose search still finds the word "IP67", and meaning search finds "ingress protection".

Check yourself

What is a chunk, and why does a text chunk never cross a page?

A chunk is one searchable card. Because each one belongs to one page, finding the chunk tells you the page to cite.

Why are table rows separate chunks and also whole tables?

A row card is small and about exactly one fact, so it ranks well for a specific question. The whole-table card helps when a question spans several rows.

What does the prefix do for "Max discharge current | 320 A"?

It adds "EV-BMS-100 Battery Management System › 3. Electrical Specifications › p.2", so the card can be matched by product name and section even though the row text never mentions them.

Where does "160 = control unit" come from?

From the patent text ("a control unit 160"), read by the numeral dictionary. Not from the drawing; OCR never sees that label.

When is an OCR'd label "repaired"?

Only when exactly one dictionary numeral explains it, by one missing leading digit or one commonly confused digit. "10" becomes 110 on the gripper because 110 is the only candidate.

Why both keyword and meaning search?

Keyword search is exact but misses paraphrases ("IP rating" vs "ingress protection"). Meaning search catches paraphrases but is weak on exact numbers and codes. The real examples in B7 show each one failing where the other succeeds.

Why is the figure description generated at indexing time and not per question?

It's done once per figure and cached, so questions stay fast and cheap. For visual questions, the image is still sent at answer time.

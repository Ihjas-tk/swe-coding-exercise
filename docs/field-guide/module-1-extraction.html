Part A

What the whole program does

A1

Start with one question

The repo is a question-answering tool for engineering documents: patents, design documents, a parts list and a test log. You ask a question in plain English. It gives an answer plus the document and page it came from. If the documents don't contain the answer, it says "not found" instead of guessing.

you type

"What is the maximum discharge current rating of the EV-BMS-100?"

→
it finds

A table row on page 2 of EV-BMS-100_design_document.pdf:

Max discharge current | 320 A | continuous, 450 A for 10 s

→
it answers
{"answer": "320 A continuous,
  450 A for 10 s.",
 "citations": [{"doc":
  "EV-BMS-100_design_document.pdf",
  "page": 2}],
 "not_found": false}

We'll follow this exact page through the rest of the guide.

A2

The five steps (the five modules)

Think of the program as a research assistant working in a small library. Each step below is one folder in the repo.

STEP 1 · you are here

Extraction

Read every file and write down what's on each page: the text, the tables and the pictures, plus where each one sits.

The assistant reads every book and takes neat notes, writing the page number on each note.

ae/extract/
STEP 2

Indexing

Cut the notes into small searchable pieces ("chunks") and file them so they can be found by keyword or by meaning.

The notes go onto index cards in a card catalogue.

ae/index/
STEP 3

Retrieval

When a question arrives, find the pages most likely to contain the answer. Questions about counts or totals go to a database query instead.

The assistant pulls the most relevant cards for your question.

ae/retrieve/
STEP 4

Answering

Claude (the AI model) writes an answer using only those pages, and code then checks it. Every number has to appear in the cited page, or the answer becomes "not found".

The assistant writes the answer from the cards and a checker confirms every claim.

ae/answer/
STEP 5

Evaluation

Measure how good each step is, using test questions with known answers.

An exam for the assistant, marked step by step.

ae/eval/
Why step 1 matters mostEvery later step only ever sees extraction's notes, never the original files. If extraction reads a table wrong or loses a page number, nothing after it can fix that.
A3

Words you'll need

text layer
The real, selectable letters stored inside a PDF. If you can highlight a word with your mouse, the page has a text layer.
scanned page
A page that is just a photo of paper. No text layer, only pixels. One patent here (US2988237A) is like this.
OCR
Optical Character Recognition: software that looks at pixels and works out the letters. We use Tesseract.
block
One piece of a page: a paragraph, a heading, a table or a figure. Extraction turns each page into a list of blocks.
bbox (bounding box)
The rectangle a block occupies on the page: left, top, right, bottom. Measured in "points" (1/72 inch). A US letter page is 612 × 792 points.
reading order
The order a person would read the blocks in. This is hard on two-column pages.
caption
The line under a picture or table, such as "Figure 2 — BMS enclosure…".
backend
One complete way of doing extraction. This repo has three: thin, docling and hybrid.
ParsedDocument
The name of extraction's output: one file → its pages → each page's blocks.
cache
Saved results, so a page is only processed once even if you re-run the program.
Part B

Step 1, Extraction, slowly

B1

Why extraction is needed: a PDF is not a document

When you open a PDF you see paragraphs and tables. The file itself doesn't store "a table". It stores drawing instructions: put these letters at this spot, draw a line from here to there. Nothing in the file says which lines form a table, which text is a heading, or what order to read things in.

what you see
ParameterValue
Max charge current120 A
Max discharge current320 A
what the file actually contains (simplified)
% draw text "Max discharge current" at x=70, y=168 "320 A" at x=250, y=168 % draw lines line from (64,160) to (548,160) line from (240,140) to (240,260) % ...hundreds more, in whatever order the % program that made the PDF chose

So extraction has to rebuild the structure: which letters form a paragraph, which lines form a table grid, which picture goes with which caption, and what order a person would read it all in. A scanned page is harder again, because there are no letters at all, only a picture of them.

B3

Four kinds of file, four different problems

The corpus has four file types. Each one is hard in its own way, so each gets different handling.

Normal PDF

3 patents + 2 design docs

Problem: the letters are there, but scattered. Two-column patents get scrambled easily, and tables and figures have to be discovered.

Solution: the five questions in B4.

Scanned PDF

US2988237A patent (2 pages)

Problem: no letters at all, just a photo of the page.

Solution: OCR with Tesseract turns pixels into words. Then the same steps as a normal PDF.

Word document

RJA-40 actuator .docx

Problem: the content is easy to read, but a .docx has no pages. Pages only exist once something lays the document out, and we need page numbers to cite.

Solution: read the content directly, then convert a copy to PDF with LibreOffice and look up which page each paragraph landed on.

Spreadsheet

test_log.csv, bill_of_materials.xlsx

Problem: questions like "how many tests failed?" need counting, and text search can't count.

Solution: load each sheet into a small SQL database so later steps can run real queries.

▸ In the code: who handles which file

ae/extract/base.py → parse(path, backend) looks at the file extension and backend and calls the right reader:

• PDF → thin/pdf.py, docling_backend.py, or parse_hybrid in base.py
• DOCX → thin/docx.py (with pagemap.py for page numbers)
• CSV/XLSX → structured.py, called directly by the ingest step (ae/index/ingest.py)

B4

The five questions asked of every PDF page

The thin backend (the one written by hand in this repo) handles a PDF one page at a time, by answering five questions in order. Once you know these five, you know how ae/extract/thin/ works.

question 1 of 5

Does this page have real text, or is it just a photo?

The code counts the letters in the text layer. Under 30 letters, with an image covering most of the page, means it's a scan. It also checks the quality of the text: some PDFs contain garbage text such as (cid:127) or random symbols. If fewer than 60% of the words look like real words, numbers or part codes, the page is treated as a scan too.

Scans go through OCR. Pages with good text skip it, which is faster and more accurate.

Why per pageOne document can mix real pages and scanned pages, so the decision is made page by page, never for a whole file.
▸ In the code

ae/extract/thin/ocr.py: needs_ocr makes the decision and text_quality scores the text. ocr_page runs Tesseract on a 300 dpi image of the page and groups its words into paragraphs.

The thresholds sit at the top of the file: MIN_TEXT_CHARS = 30, MIN_TEXT_QUALITY = 0.6, OCR_DPI = 300.

question 2 of 5

Which bits of text belong together, and what is each bit?

The PDF library (PyMuPDF) gives back text already grouped into rough blocks, but sometimes it splits one paragraph into two. The code glues pieces back together when they sit right on top of each other with the same font size.

Then each block gets a role, decided by simple rules:

• starts with "Figure 2 —" or "FIG. 3" → caption
• bold or bigger than normal text → heading
• short line at the very top or bottom of the page → header/footer
• anything else → body

Why roles matterHeadings become titles for tables ("3. Electrical Specifications"), captions get attached to figures, and headers/footers are ignored later so they don't clutter search results.
▸ In the code

ae/extract/thin/text.py: raw_blocks_from_page asks PyMuPDF for blocks, merge_adjacent glues split paragraphs, classify_role applies the role rules, and build_text_blocks runs all three in order.

question 3 of 5

In what order would a person read these blocks?

This is the classic trap with patents, which are printed in two columns. The obvious approach, "sort blocks top to bottom", reads across both columns line by line and mixes the two texts into nonsense. Our approach finds the columns first, then reads down the left column before moving to the right. Try both on this mock patent page:

How "columns first" works, in plain words:

1. Blocks that stretch across the whole page (a title, a section banner) act as dividers, cutting the page into horizontal strips.
2. Inside each strip, look for a vertical gap with no text in it. That gap is the space between columns.
3. Read each strip: left column top to bottom, then right column top to bottom, then move to the next strip.

▸ In the code

ae/extract/thin/text.py: detect_columns finds the gaps (a gap must be wider than MIN_GUTTER = 12 points), and order_blocks does the strip-then-column reading. A block counts as full-width if it's wider than 62% of the text area (FULL_WIDTH_FRAC).

PyMuPDF has a built-in sort=True option, and it's exactly the "top-to-bottom (wrong)" button above. That's why the repo writes its own.

The same function runs a second time after tables and figures are found, so they're placed in reading order too.

question 4 of 5

Is any of this a table?

The spec tables in the design documents are drawn with lines around every cell. A library called pdfplumber finds those lines, sees where horizontal and vertical lines cross, and works out the grid of cells from the crossings.

Then each cell is filled with the words that sit inside it. Those words come from a different library (PyMuPDF), because pdfplumber garbles some symbols, turning "≥" into "‡".

Any loose text that sat inside the table area is removed, because the table already contains it and we don't want it twice.

Why it matters for our exampleBecause the row stays a row, "Max discharge current" and "320 A" stay linked. A plain text dump could jumble them with the neighbouring rows.
LimitA scanned page has no drawn lines, only pixels, so this method can't find tables on scans. That's the main reason the hybrid backend exists (B5).
▸ In the code

ae/extract/thin/tables.py: extract_tables runs pdfplumber's find_tables. It first uses the "lines" method and only falls back to guessing columns from text alignment if no lined table exists, with strict checks, because guessing found a fake 19×8 table on a patent page. _fill_cells puts the PyMuPDF words into cells. _title_for attaches the nearest heading above as the table title. drop_text_inside_tables removes the duplicates.

question 5 of 5

Are there pictures, and which caption belongs to each?

Find: PyMuPDF reports where every image is placed on the page. Line drawings that aren't images get grouped into clusters. Anything smaller than about 2 cm (60 points) is skipped as an icon.

Save: each picture area is cut out and saved as a PNG file. Later, an AI model looks at these to describe them.

Caption: the nearest "Figure N…" or "FIG. N…" text just below the picture (or above, as a second choice) becomes its caption. If a picture sits at the bottom of a page with no caption, the code checks the top of the next page. That's how our example's Figure 2 got its caption from page 3.

Labels: patent drawings have numbers pointing at parts ("160" = control unit). OCR reads those numbers off the image so the figure can be found by them.

▸ In the code

ae/extract/thin/figures.py: find_figure_boxes, crop_figure, link_caption and ocr_labels, all called by extract_figures.

ae/extract/thin/pdf.py: _figures_from_scan handles scanned pages, where the whole page is one image, so it guesses each picture's area from where its caption sits. _link_cross_page_captions handles the caption-on-next-page case.

pdf.py also contains _parse_page, which runs questions 1–5 in order for one page. It's the best single function to read first.

B5

Three "readers": thin, docling and hybrid

Everything in B4 describes thin, the reader written by hand from small tools. The repo also has two other readers. All three produce exactly the same output format, so the rest of the system doesn't care which one ran, and they can be compared fairly.

reader 1

thin

Likesomeone with a ruler and a checklist of rules.

Hand-written rules on top of PyMuPDF, pdfplumber and Tesseract. Every decision can be explained line by line. Very accurate on normal PDFs. Blind to tables and uncaptioned pictures on scanned pages.

reader 2

docling

Likean AI that looks at a photo of the page.

An open-source IBM library. A trained AI model spots headings, tables and pictures by looking at the page image, and a second model reads table structure. It can find tables on scans. On our scanned patent, though, it wrote some text twice and matched several captions wrongly.

reader 3 · the default

hybrid

Likethe ruler-and-checklist person, who calls in the AI only for photographed pages.

Runs thin on every page. Only on scanned pages, it also runs docling and borrows docling's tables and pictures, while keeping thin's text. Each reader is used where it did best in testing.

▸ In the code

ae/extract/docling_backend.py runs docling and converts its output into our format. It forces docling to use Tesseract for OCR too, so the comparison is about layout, not about which OCR engine is better.

ae/extract/base.py: parse_hybrid and _merge_layout are about 50 lines that show the whole hybrid idea. If docling's table covers some of thin's text, that text is dropped. If docling's picture overlaps a picture thin already found, thin's is kept.

+

The Word and spreadsheet paths, briefly

Word (.docx)

A .docx is a zip of XML files that lists paragraphs, tables and images in order. Reading it is easy and exact, using the python-docx library. The only missing piece is page numbers.

So the code asks LibreOffice (free office software) to convert the document to PDF, then searches that PDF for the first few words of each paragraph to learn which page it landed on.

Real snagThe RJA-40 spec table gets split across pages 1 and 2 in the LibreOffice version. The code records each piece on its own page and gives both pieces the same table ID.
▸ In the code

thin/docx.py reads the XML. pagemap.py does the LibreOffice conversion (render_to_pdf), the page lookup (PageLocator) and the table splitting (tables_by_page). Without LibreOffice installed, everything is reported as page 1, and the output says so.

Spreadsheets (.csv, .xlsx)

Each sheet becomes a table in a small SQLite database file. The code works out which row is the header and whether each column holds numbers, dates or text, so a later step can ask things like "count the failed tests".

It also writes each row out as one line of text ("test_log row 7: result=FAIL; …"), so rows can be found by ordinary search as well.

Why not treat them as textTurning a spreadsheet into prose makes "how many" and "highest" questions unreliable. A database answers them exactly.
▸ In the code

structured.py: load_structured loads files, _infer_type guesses column types, and query_sql runs queries safely: read-only, one SELECT statement only, with a time limit.

Cache: every processed page is saved as a small JSON file under data/cache/. Re-running costs nothing unless the file or the code version changes. This matters for a 100-page PDF, because docling takes about 3 seconds per page. (ae/extract/cache.py, 43 lines)

B7

What still goes wrong (real examples)

You'll be asked where your tools break. These are the cases found in this corpus, in plain words.

The overprinted table cell

In the Falcon-VT1 document, the PDF itself prints "MHz" and "with" on top of each other, so the value spills into the next column. Every reader tested gets this wrong. It's 2 cells out of 30, and it's a flaw in the file, not in the code.

OCR eats a "1"

In patent drawings, the pointer line touches the digit, so Tesseract reads "110" as "10". The next step (indexing) repairs this using the patent text, which names every numbered part.

A label outside the picture

The gripper patent's label "160" is printed just outside the embedded image, so no amount of image reading finds it. The patent text still defines it, so the answer is found that way.

Docling writes text twice

On the scanned patent, docling outputs the top-of-page text twice. Switching its OCR engine didn't help, so the fault is in its layout step. Hybrid avoids it by using thin's text.

Page numbers disagree with the test set

Two test questions cite a different page than the one the content actually renders on (EV-BMS-100 IP67; the RJA-40 table split). The answers are right; the page conventions differ. Both are documented in the README.

One reading-order slip

On page 1 of the UAV patent, a right-column header line gets read in the middle of the left column. Docling's AI gets this page more right than thin's rules.

?

Check yourself

Try answering each question out loud before opening it. These are the questions the brief says the interview will cover.

When does OCR run?

Page by page: when a page has almost no text and is covered by an image, or when its text looks like garbage (under 60% real-looking words). Tesseract does the OCR.

How do you avoid mixing up two columns?

Full-width blocks divide the page into strips. Inside each strip, a vertical gap marks the columns. Read the left column fully, then the right. It's not a simple top-to-bottom sort, because that interleaves the columns.

How are tables found?

pdfplumber finds the drawn lines and builds cells from where they cross. PyMuPDF words fill the cells. This can't work on scans (no lines), so hybrid borrows docling's AI table detection there.

How are figures found and captioned?

From image positions and clusters of line drawings. Each is cut out as a PNG. The nearest "Figure N" text below (or above) is its caption, with a fallback to the top of the next page.

Why is hybrid the default?

Thin had far cleaner text on our scanned patent (0.13% vs 21.8% letter errors) and matched all captions. Docling was the only one that could find tables and pictures on scans. Hybrid uses each for what it measured best at.

Why does a Word file need LibreOffice?

A Word file has no pages until it's laid out. Answers must cite pages, so we lay it out with LibreOffice and look up where each piece of text landed.

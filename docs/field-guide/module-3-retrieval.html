A2

New words for this sheet

route
Which way a question is handled: numeral (dictionary lookup), sql (database query) or hybrid (search). Search always runs, whatever the route.
rank
A result's position in a list: 1st, 2nd, 13th… The merging step uses ranks, not raw scores.
RRF
Reciprocal Rank Fusion: a simple way to merge two ranked lists. Each list gives a chunk 1 ÷ (60 + its rank) points, and the points are added.
page score
How promising a whole page is: its best chunk, plus a little credit for other good chunks on it.
hard filter / soft boost
A hard filter searches only one document. A soft boost just nudges that document up the list.
alias
Other names a document is known by: its patent number in several spellings, or the product code (EV-BMS-100).
text-to-SQL
Claude turns a question into a database query, which the code then runs on the spreadsheet tables.
Recall@k
How often the correct page is somewhere in the top k pages. Recall@5 = 0.9 means the right page was in the top 5 for 90% of questions.
Part B

Step 3, Retrieval, slowly

B1

Three routes, and a safety net

Different questions need different tools. "How many tests failed?" needs counting, so a database. "What is labelled 160?" needs the patent dictionary from sheet 2. Most questions need search. The code picks a route with simple rules, and always runs search as well, so a wrong route can't lose the answer.

Why rules, not an AI routerThe question parser is a set of regular expressions, not a model. The research notes found simple rule or TF-IDF routers beat embedding classifiers on routing benchmarks. Rules are also instant, free, and easy to explain. Because search always runs alongside, a rule that misfires costs little.
B2

Reading the question

Before any searching, the code scans the question for six kinds of clue. None of this uses AI.

1 · Identifiers

Exact codes, using the same rules as sheet 2: "EV-BMS-100" → ev-bms-100, "US8,485,576 B2" → us8485576b2, "160" → ref160 (only if 160 is in the dictionary).

2 · Which document?

A patent number names exactly one document, so search is restricted to it (hard filter). A product name like EV-BMS-100 also appears in test-log and parts-list rows, so it only gets a small boost (soft).

3 · A figure?

"FIG. 2", "Figure 3" → remembered, so the answer can cite the figure's page.

4 · A part number?

"labelled 160", "component 18", "112 in FIG. 2" → if that number is in the dictionary, choose the numeral route.

5 · Counting + spreadsheet words?

A counting word ("how many", "highest", "total", "distinct"…) and a spreadsheet word ("test log", "failed", "unit cost", "BOM"…) → choose the sql route. Both are required.

6 · Is it visual?

"how many … shown in Figure 2", "where is", "colour" → flag it, so step 4 attaches the figure image for Claude to look at.

▸ In the code

The rules are the regular expressions at the top: NUMERAL_Q_RE, NUMERAL_Q2_RE, AGG_RE (counting words), STRUCT_VOCAB (spreadsheet words), VISUAL_RE.

doc_aliases builds each document's alternative names from its file name, patent-number spellings, and product codes found on page 1. For the gripper patent: us8485576b2, us8485576, 8485576, gripper, …

Run make ask Q="…" DEBUG=1 to see the route and reasons for any question. Tests: tests/test_routing.py.

B3

Route 1: the dictionary lookup

For "What component is labelled 160 in FIG. 2 of US8,485,576 B2?" the parser found a patent number (search only the gripper patent), a figure (FIG. 2), and a known numeral (160). So it looks 160 up in the dictionary from sheet 2 and writes a plain-English note that goes into the evidence. This is the real note:

Reference numeral 160 in US8485576B2_robotic_gripper.pdf is defined in the specification as: control unit. Defined on page(s) 1, 2. FIG. 2 is described as: perspective cross section of an apparatus of the present invention and a pin locking mechanism … in an unlocked configuration (page 1). (label 160 was not read on the FIG. 2 image; the definition comes from the specification text)
Why say "not read on the image"Honesty about evidence strength. The definition is certain; whether 160 is actually visible in FIG. 2 isn't confirmed. Claude sees that caveat and can word the answer accordingly.

When the number is ambiguous

If no document is named and two patents both define the same numeral, the note says so: "defined in several documents… the question must name the document". Claude then asks for clarification or declines instead of guessing.

▸ In the code

This route lives in ae/answer/pipeline.py, not in ae/retrieve/: Engine._numeral_lookup and _numeral_seen_in_figure, which checks the figure chunk's confirmed labels from sheet 2's repair step.

B4

Route 2: asking the database

Counting questions go to the spreadsheet tables loaded in sheet 1. Claude is shown a description of the tables (column names, types and sample values) and asked to write one SELECT query. The code runs it read-only and puts the result rows into the evidence. Three real examples:

question · q17How many test runs failed in the test log?
Claude wrote
SELECT COUNT(*) AS failed_tests
FROM test_log
WHERE result = 'FAIL'
result7 · from test_log.csv
question · q18How many distinct EV-BMS-100 units were tested?
Claude wrote
SELECT COUNT(DISTINCT unit_sn)
FROM test_log
WHERE unit_type = 'EV-BMS-100'
result18 · from test_log.csv
question · q19Which part has the highest unit cost?
Claude wrote
SELECT part_number, unit_cost_usd
FROM bill_of_materials
WHERE part_number IS NOT NULL
ORDER BY unit_cost_usd DESC LIMIT 1
resultRJA-GEAR-101 · 315.75 · from bill_of_materials.xlsx

What Claude is shown (excerpt)

TABLE "test_log" -- source file: test_log.csv, 109 rows
  "unit_type" TEXT -- 3 distinct; values: EV-BMS-100, Falcon-VT1, RJA-40
  "result" TEXT -- 2 distinct; values: FAIL, PASS
  ...

Listing the exact allowed values ("FAIL", not "failed") is what lets Claude write result = 'FAIL' correctly the first time.

SafetyThe query runs on a read-only connection. Only a single SELECT is allowed, words like DELETE or DROP are rejected, and a time limit stops runaway queries. If the query errors, Claude gets the error message and one chance to fix it.
The "IS NOT NULL" detailSpreadsheets often have total or subtotal rows with a blank label. The prompt tells Claude to exclude them for "which item is largest" questions, which is why q19's query has WHERE part_number IS NOT NULL.
▸ In the code

ae/retrieve/sql.py (46 lines) → answer_sql: builds the prompt from describe_schema, calls Claude through ae/llm.py (responses cached in data/cache/llm.sqlite), runs query_sql, and retries once on error. The safety checks themselves are in ae/extract/structured.py → query_sql (sheet 1).

If the SQL route fails completely, pipeline.py catches it and the question is answered from search results alone.

Route 3: search, merge, pick pages

This runs for every question. We'll follow the running example, "What is the maximum discharge current rating of the EV-BMS-100?", through its five steps with the real numbers.

Keyword search is fooled: test-log rows contain "EV-BMS-100" as an exact identifier, while the answer row's text never says the product name. Sheet 2 showed this with a top-3 search (answer 2nd). With the full top 50 the identifier bonus spreads over more test-log rows and the answer drops to 13th.

Merge the two lists by rank (RRF)

The two searches score on completely different scales: BM25 points versus similarity between 0 and 1. Adding the raw scores would be meaningless. So each list just gives every chunk 1 ÷ (60 + its rank) points, and the points are added. Being near the top of either list helps; being near the top of both helps most.

Slide to 51 for "not in that list". Starts at the answer row's real ranks (13 and 1). Compare: test_log row 1 was 1st and 22nd.

Why k = 60The 60 stops the top ranks from dominating: 1st gets 1/61 and 10th gets 1/70, not ten times less. It's the standard default from the original RRF paper. A tuned weighted blend would need many labelled questions to tune on, and this project has 20.

Guarantee exact identifier matches

If the question contains an identifier that exists in the index (a part number, a patent number, "160"), every chunk carrying it is added to the candidates even if neither search ranked it in the top 50. An exact code match is too strong a signal to lose to ranking noise.

Group chunks into pages and score each page

Answers cite pages, so pages are what's ranked and returned. A page's score is:

best chunk + 0.1 × (next three chunks on the page) + 0.004 if the question named this document

Why only 0.1 × supportThe test log is one "page" holding 109 rows. If every matching row counted fully, that page would win every question just by size. Capping support at three chunks, at a tenth of their weight, stops it flooding.
Notice the boostThe test log contains "EV-BMS-100" too, but spreadsheets are deliberately excluded from the named-document boost, since a product name appears all over the parts list and test log.

Keep the top 8 pages and fill in their neighbours

The best 8 pages are kept. Each carries its matching chunks first, then other chunks from the same page in reading order, up to 10. Claude sees the answer row with its surroundings: the rest of the table, the heading and so on.

The code also records a few signals about how confident retrieval looks (top score, whether both searches agree on a top-5 chunk), which step 4 can use to decline.

▸ In the code

ae/retrieve/hybrid.py (100 lines) → retrieve does all five steps; rrf is 6 lines. Constants at the top: RRF_K = 60, TOP_N = 50, MAX_PAGES = 8, MAX_CHUNKS_PER_PAGE = 10, DOC_BOOST = 0.004 (about one rank step at the top).

A hard filter (patent number) is passed as doc= into both searches, so they only look inside that document.

The mode parameter ("bm25", "dense", "hybrid") switches searches off for the evaluation's comparisons. The gate signals are returned in RetrievalResult.gate.

B6

Does it work? The recall numbers

The evaluation (sheet 5) checks, for each of the 20 answerable dev questions, whether the correct page appears in the top k pages. These are the hybrid-backend results:

search usedcorrect page 1stin top 3in top 5in top 10
keyword only60%85%90%90%
meaning only75%95%95%100%
both, merged (what ships)75%90%90%100%
Honest readingOn these 20 questions, meaning search alone matches or slightly beats the merged search. One question is 5 percentage points, so 90% vs 95% is a single question and within noise. Expect to be asked: "why not just use dense search?"
The answerDense search fails on exact codes and bare numbers. B7 on sheet 2 showed it ranking the page title first for "labelled 160". The hidden test set will have more such questions, and the identifier guarantee needs the keyword index. The merged search costs nothing at top 10 (100%), and Claude receives 8 pages, so "somewhere in the top 8" is what really matters.

The same evaluation also removed chunk kinds one at a time. Without row chunks, table questions found the right page first only 43% of the time instead of 71%. That's the measured case for sheet 2's "one row = one chunk" decision.

B8

Limits and loose ends

Mixed-case product codes

"Falcon-VT1" isn't detected as a product code, so its document gets no boost. It still works on the dev set, but a harder question could miss.

Retrieval "not found" gate is off

Confidence signals are computed, but the threshold (min_top_score) defaults to 0 everywhere, so retrieval never declines by itself. All "not found" decisions are made in step 4's checks. The README lists tuning this gate as future work.

Small test set

20 answerable questions, all over 7 documents. The README suggests adding distractor documents to see whether recall holds when there's more to get lost in.

Code tidy-ups an interviewer might spot

In parse_query, the first hard = … line is immediately overwritten by the second. In pipeline.py, the "scope gate" if block ends in pass and does nothing. Both are harmless.

Check yourself

What are the three routes, and which one always runs?

Numeral (dictionary lookup), sql (database query), hybrid (search). Search always runs, so a wrong routing decision can't lose the answer.

Why is a patent number a filter but a product name only a boost?

A patent number identifies exactly one document. A product name like EV-BMS-100 also appears in test-log and parts-list rows, which may be where the answer is.

Why merge by rank instead of adding scores?

Keyword and meaning scores are on different scales, so adding them is meaningless. Ranks are comparable. RRF gives 1/(60+rank) from each list.

For the 320 A question, keyword search ranked the answer 13th. How did it still end up first?

Meaning search ranked it 1st. Its merged score, 1/73 + 1/61 = 0.0301, beat the test-log row that was 1st and 22nd (1/61 + 1/82 = 0.0286). Its page then got the named-document boost; the test log didn't.

Why can't the 109-row test log win every question?

A page's score is its best chunk plus only 0.1 × its next three chunks, so many weak matches can't add up to a win.

How is "How many test runs failed?" answered?

Counting word + spreadsheet word → sql route. Claude sees the table description, writes SELECT COUNT(*) … WHERE result = 'FAIL', and the code runs it read-only and gets 7.

Dense search alone scored as well. Why keep both?

The difference is one question (noise). Dense fails on exact codes and numbers, which the hidden test will contain, and recall at 10 is 100% either way.
